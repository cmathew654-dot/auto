  <action>
Next to the existing `WorkflowStep` type and `demoRunStepOrder`, add and export:

```ts
export interface DemoTourAccount {
  accountNumber: string;
  totalRows: number;
  eligibleCount: number;
  withheldCount: number;
}

export interface DemoTourStep {
  id: string;
  stage: WorkflowStep;      // which stepper stage this step lights up
  title: string;            // recruiter-legible headline
  body: string;             // what just happened
  proof: string;            // what it proves
  nextLabel: string;        // Next button text; last step reads "Done"
  fillAccountNumber?: string; // when set, advancing INTO this step fills that account first
}

export function buildDemoTourSteps(accounts: DemoTourAccount[]): DemoTourStep[]
```

Shape of the returned list (order matters, and it is what the test pins):
1. `load` stage — headline about the CSV being read in the browser. Body: the sample was parsed
   locally. Proof: no upload, no account, no project server — the file never leaves the browser.
2. `review` stage — headline about every row getting a verdict. Body: state the total row count
   and the account count from `accounts` (derive, do not hardcode). Proof: a human sees every
   verdict before anything is entered anywhere.
3. `packet` stage — headline about only approved fields being packaged. Body: only rows that
   cleared review go into the fill packet. Proof: blocked rows physically cannot reach the
   destination page.
4. One `fill` stage PER account, in the order given, `id: 'fill-' + accountNumber`,
   `fillAccountNumber: accountNumber`. Copy is derived from that account's counts:
   - When `withheldCount === 0`: say all N rows landed and that this is what a clean account
     looks like — the baseline for the next one.
   - When `withheldCount > 0`: say `eligibleCount` of `totalRows` landed and `withheldCount` were
     held back, name the two kinds of stop (rows waiting on a manual-review override vs. a row
     with no ticker or CUSIP that can never be auto-entered), and point out that the panel above
     shows only what passed. Proof: the gates are doing judgment, not breaking.

Every fill step's copy must also make clear that Save is a human click and that this destination
panel is simulated, not eMoney. Write for a recruiter with no context: short sentences, no
internal jargon (no "packet payload", no issue codes like CASH_SPECIAL_HANDLING in the visitor
copy — say "a cash row that needs a human decision").

Empty-input rule: if `accounts` is empty (nothing in the file cleared review, so there is no
packet and nothing to fill), return ONLY the `load` and `review` steps — no packet step, no fill
steps. That matches `demoRunStepOrder(false) === ['review']`: the tour must never claim a packet
or fill stage that did not happen.

`nextLabel` is a forward-looking prompt for every step except the last, which is `'Done'`.

Keep the function pure: no DOM, no timers, no reads of module state. `demoRunStepOrder` stays
exactly as it is (demo-flow.test.cjs pins it).
